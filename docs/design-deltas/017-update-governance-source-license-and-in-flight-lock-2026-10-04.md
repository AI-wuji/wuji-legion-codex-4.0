# 017：来源许可准入与在途更新锁（2026-10-04）

## 具体缺口

T24 原先只有治理报告、源码哈希和旧封包身份回读，不能证明来源版本经过明确许可准入，也不能证明任务进入执行后不会被热覆盖。该增量只补这两个确定性内部缺口，不把本地白名单当作法律意见，也不把隔离单测当作宿主或专业效果证据。

## 最小实现

- `SourceRecord` 以 `scope + id + version` 形成稳定来源引用，保留 locator、内容哈希、读取范围、许可标识和许可证据引用。
- `LicensePolicy` 要求显式 scope、允许列表和拒绝列表；来源必须通过同 scope 的显式策略，重复版本或内容哈希变化均拒绝。
- 在途任务保存精确 `release + release_sha256 + source_refs` 锁；来源必须已准入且未撤销。
- 新来源版本可以作为候选登记，但不能改写已有在途任务；不同 release、哈希或来源集合需要新的任务锁。完成只释放原锁，不能把新版本热注入旧任务。
- 事件使用幂等键和内容哈希，重复请求只回放相同结果，改 payload 失败关闭。

## 当前证据与边界

Rust 隔离测试覆盖显式许可拒绝、版本保留、跨 scope 来源键隔离、在途锁固定、候选新版本不热替换和完成收口。`tools/run_t24_evidence.py` 重新运行隔离核心测试并绑定源码哈希及现用配置前后哈希。

这不证明外部来源的法律许可结论、用户 ACL、原生宿主模型/配额，也不执行 P7、修改 Codex 配置或关机。T24 仅在这些确定性本地场景和当前回归日志均新鲜时计入；其余 95 项验收仍按各自证据状态记录。
