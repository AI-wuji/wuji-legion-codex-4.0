# 无极军团 5.0：阿极直带专家与并发执行方案

- 状态：5.0当前架构与实施基线；Codex / 本项目已默认采用5.0直接专家通路。4.0底层实现和兼容通路保持不变。
- 日期：2026-10-25
- 目的：保留5.0架构决策与实施进度，供后续对话从已完成工作继续。
- 范围：阿极直带专家、MoE式全角色冷态管理、工作流配方、专业能力引用、并发和持续执行。
- 边界：本项目入口已采用5.0；不因此改动用户级文件、模型通道或4.0兼容执行实现。不宣称所有专业运行效果或宿主原生并发已通过。

## 1. 决策摘要

> **阿极是唯一用户入口、轻量协调者和默认执行者，直接按需调用专家；参谋部和主帅不再是必经代理层。主帅积累的专业组织经验转为阿极可检索、按需加载的工作流配方。所有角色（包括参谋职责、主帅/工作流角色、专家和方法角色）均为MoE式冷态资源，只在任务匹配时启用所需分身，结束后挂起/释放。已就绪的独立任务尽早并发，只有真实依赖、冲突、资源或权限边界才串行。**

同一专精专家可按来源/对象范围启动多个分身；只有职责、方法或工具边界实质不同才另设专家。方法、Skill、MCP、CLI/API按真实消费者赋能，不把所有能力常驻塞给阿极。阿极承接原参谋部的任务拆解、依赖识别、专家路由、并发控制和统一交付。

此结构的目标是减少不必要的代理跳转和墙钟等待，不保证必然减少总token；并发分身可能提高总调用量。只有宿主提供真实工具/委派能力时才能宣称相应动作已执行。

## 2. 目标、约束与继承优势

- 阿极唯一沟通与交付；轻任务直办，不为显示专业强制上专家。
- 能并行处理的同类任务应按范围扇出（例如GitHub、官方网页、论文来源），不同专业但无依赖的分支也可并发。
- 除真实数据依赖、共享写冲突、宿主资源/并发限制、必要输入或权限边界外，不人为串行。
- 任务持续推进；用户插话先答，再恢复原目标，除非明确取消或替换。补充信息只更新受影响分支，不重放已完成副作用。
- 不做仪式性验收。用户要求、具体重要风险，或结果不可观察且检查会改变下一步时，才做一次最低成本核验；足够即停。
- 对用户与角色交互均采用简洁回执：只传必要目标、上下文、产物、依据、状态、风险和阻塞，不要求/传递冗长思考过程。
- 继承4.0的懒人模式、白帽、证据优先、最小权限、冷态按需加载、真实产物/hash、局部失败恢复和大输出代码侧聚合。
- 不新建常驻调度平台；复用现有宿主委派、工具和项目执行接口。

## 3. 运行模型：阿极直接协调

阿极处理用户目标与授权，必要时加载工作流配方，从轻量专家索引选择角色与能力，形成有限任务分支。每个分身只获得自己的任务范围与所需输入，完成后将简短结果交回阿极；阿极整合并对用户交付。

- **阿极**：常驻轻量入口、默认执行者、任务拆分/路由/并发与权限监督、结果整合者。阿极不常驻加载所有专家正文。
- **参谋部职责**：保留任务分类、拆分、依赖图、资源共享和回交组织等方法，但由阿极直接承担；不为这些职责再启动必经代理。
- **主帅经验**：转为可检索工作流/配方，记载触发条件、常见子任务、专家/能力选择、依赖/并发关系、必要检查触发条件和局部失败处理。配方是知识，不是强制代理或审批链。
- **专家**：定义保持专精，可按互斥任务范围开多个分身。只加载职责卡和本任务所需方法/工具引用。
- **工作流/专家团**：需要组织知识时直接调用配方；只有确有独立角色产出的任务才实例化相关角色。配方不自动召集全体候选专家。

不再默认执行“阿极→参谋部→主帅→专家”。目标是“阿极→必要的专家分身”，其中工作流作为按需知识，不增加指挥层。复杂性来自任务真实依赖，而不是角色层级数量。

## 4. 全角色MoE冷态生命周期

MoE按需激活适用于无极所有运行角色，而非只适用于专家：参谋职责、主帅/工作流角色、专家和方法角色均以冷态定义保存。阿极保持轻量协调入口。

- 默认角色状态为冷态/挂起，不运行、不预载全员、不占模型调用或并发槽。
- 命中任务后只激活必要的任务分身，只加载该分身的职责、必要上下文和能力引用。
- 同一专家多个分身必须有互斥范围或独立交付；共享写入时串行或由单一owner写入。
- 完成、取消或不可继续后关闭并释放实例；角色定义和可复用方法保留，活跃上下文不常驻。
- 等待必要依赖时只保留最小检查点。若宿主不支持真正暂停/恢复，则关闭实例、用宿主已有恢复机制续接，不声称原进程仍挂起。
- 这里的MoE是外层角色路由与激活策略，不断言底层模型采用Mixture-of-Experts网络结构。

## 5. 上下文连续性：压缩后从真实状态续做

压缩、换会话或释放分身时，复用宿主已有的continuation/handoff机制、工作区产物、工具回执和来源/hash；不新建第二记忆库、常驻memory agent或对话镜像。仅长任务、跨上下文/角色交接、多未完成分支、重要副作用或即将压缩时记录短恢复包；简单且可从当前上下文直接恢复的任务不存档。

恢复包只保留能改变下一步的信息：原始目标/授权/禁止项；已完成动作与真实产物/回执及必要路径/hash；未完成分支、依赖/并发关系和各自下一动作；failed/unknown/blocked等真实状态及具体缺口；关键结论的来源引用与unknown；仍活动的角色/槽位；一个明确的恢复后下一步。避免复制完整聊天、专家思考过程和无关历史。

压缩前交给宿主原生续接机制；仅当它无法携带必要状态且任务仍未完成时，才在任务工作区写短恢复说明。新上下文先读恢复包和必要引用，再按实际回执续接：不重复已完成动作，独立未完成分支继续，unknown副作用先查询原调用/目标再决定，不盲目重发。用户插话先答后继续原目标，明确取消/替换才停止。临时恢复摘要在任务完成后不自动晋升为长期记忆。

吸收4.0已审查的ECC“完成后记可复用状态”、Context Mode“大输出先代码侧聚合、只带必要字段与回读引用”、仓颉式资料蒸馏“核心方法/判断标准/边界/依据保留来源”；不搬入额外hook/MCP/SQLite或第二索引库。既有来源处置见`docs/external-capability-adoption-2026-10-13.md`，本节是其5.0执行落点，不代表本轮复核外部项目最新版本。

## 6. 任务链与并发规则

### 5.1 最短路径

- 0个专家：阿极直办。
- 1个专家：阿极直接调用该专家；若无多分支/协同依赖，不增主帅层。
- 多个专家/分身：阿极只分配存在独立产物的工作，明确输入、写集、依赖和简短回交格式。
- 技能或MCP单次使用不自动变成组队任务；其使用者可为阿极或当前专家。

### 5.2 并发

所有已就绪、互相独立、权限允许、没有冲突写集的工作尽早启动。适用示例：全网研究同时开GitHub搜索、官方文档/网站搜索和论文检索；同一搜索专家也可按不同平台/关键词/范围运行多个分身。

只有以下情况串行：后一步必须消费前一步真实产物；同一文件/资源存在冲突写入；用户授权或权限范围不同；宿主并发槽/调用额度限制；必要条件尚未具备。分支受阻不拖停无依赖工作，完成一支即可推进其下游，不必等所有平行分支都结束后才继续。

不以固定人数、固定并发数字或角色图大小作为效率目标；优先沿用宿主自然限流和共享并发槽。未知是否结束的宿主调用不盲重试，也不能当作已释放槽位。

### 5.3 同专家多分身还是多专家

同一方法、不同互斥来源/对象范围：使用同一专家多个分身，降低定义与上下文冗余。专业方法、工具能力、权限边界或交付物不同：拆成不同专家。多个分身只因并发启动，不要求为每个方向永久维护一个新专家。

## 7. 工作流配方与专家赋能

每份配方要直接指导执行，至少说明：任务触发/不触发、子任务拆分、需要的专家角色ID与选择条件、需要加载的Skill/MCP/CLI/API、独立分支与真实依赖、结果汇总方式、局部失败降级、少量必要的风险检查触发条件。

专家卡按真实消费者维护：职责目标/边界、适用输入、预期产物、所需方法和工具引用、并发/依赖条件、权限限制及失败处理。没有消费者的冷专家不批量填充。现有目录的角色声明不代表Skill安装、工具授权或运行Agent已存在。

专业能力优先复用本机现有Skills、MCP、CLI/API和项目原生工具。来源研究要有实际消费者，优先官方文档与成熟项目的可复用方法；不为统一架构整包搬运或新造调度器。只有能力确实缺失且采用会影响当前交付时才评估新增绑定。

## 8. 多来源并发研究的首个配方

用户需要跨站点/平台研究时，阿极把同一问题切为互斥来源范围：GitHub/代码仓库、官方产品/标准文档、论文/研究、用户点名的网站等；仅启动本次确有价值的分支。分支回报结论要点、原始来源、版本/日期、支持或反证、缺口/失败。阿极去重、比较证据并作决策总结。

来源分支彼此独立时立即并发。先后依赖真实搜索结果的追问作为后续增量；某一站点拒绝访问不阻塞其他来源。搜索能力以当前宿主真实提供的浏览器、网页搜索、GitHub/API或连接器为准；不可用时明确缺口或使用已授权替代。文件回执与网页搜索不是同一种能力，不能用文件执行桥冒充搜索结果。

## 9. PonyTail方法的全局扩展

从PonyTail蒸馏的是“最小充分行动、结果优先”，不是照搬其代码专用方法或benchmark数字：已有结论优先复用；选最短正确路径；少说但完成；验证只匹配用户要求与实际风险；专家之间传最少必要信息；事实、未知和权限不能为简洁而抹掉。专业方法按领域单独赋能。

已对照公开成熟实践后采用按需技能、简单任务直办、复杂任务可分支并发和风险匹配检查；拒绝把固定多层代理、强制长计划、全量专家预载、每一步验收作为通用默认。外部项目star数或作者自报性能不等同于无极运行效果证据。

## 10. Codex原生直接专家通路与辅助执行器

- 日常5.0专家入口是Codex当前会话原生子代理，不要求用户运行CLI或写JSON；阿极直接按任务调用必要分身并发编排。
- `tools/run_legion_task.py::execute_aji_direct_experts` 与 `tools/legion_pipeline.py::execute_direct_experts` 是可复用的有界契约/诊断实现，不冒充当前对话代理通路。
- 原生专家回传当前任务结果和来源；代码契约中写入产物仍按路径/scope/hash作相应检查，不将该契约检查强加为每步默认验收。
- 未知提交不重发；该分支依赖项阻塞，但独立分支继续。
- 由阿极负责汇总，不调用主帅aggregate。
- Codex当前会话原生 `spawn_agent` / `send_input` / `wait_agent` / `close_agent` 是首选执行桥，阿极按任务直接调用和管理必要专家分身。现有CLI/app-server执行器仅作辅助或诊断，不能替代当前会话原生委派。本轮没有为验证而额外发起专家模型调用；未实际调用时不声称专家已实跑。
- 原`delegate`与`execute_delegation`4.0路径保持原状，供兼容/旧CLI场景使用；不是5.0默认路径。

## 11. 实施进度与剩余边界

已落地：
1. 5.0目标实施方案、4.0→5.0迁移差异映射。
2. 5.0活动入口说明及`legion/task-entry-5.0.json`，含阿极直带、全角色MoE冷态生命周期、并发、插话续办、按需检查和上下文连续性约束。
3. 多来源并发研究配方、现有Skill/专家映射索引。
4. 阿极直派专家执行入口、有限执行函数及本地Codex app-server辅助适配（非首选执行桥）。
5. 上下文连续性协议：长任务/跨上下文时最小恢复包，复用原生handoff与产物/hash，不建第二记忆库；ECC、Context Mode和仓颉式蒸馏按4.0已有研究结论择取方法。
6. 定向测试覆盖直派跳过参谋/主帅、同专家分身并发、真实依赖串行、unknown不重试且独立分支继续、只读结构化回执、未知专家拒绝调用。

有明确边界：
- Codex / 本项目默认入口已采用5.0；本轮未改用户级文件、模型通道或权限，4.0底层实现与兼容通路不变。
- 本轮同步文档、Skill和manifest并更新5.0项目路由；没有为验证而额外发起专家模型调用。现有CLI/app-server不是当前会话原生委派的等价桥；fixture仅验证本地契约，不证明原生专家实跑。
- 后续专家按真实任务触发补齐，不追求把58项冷目录全部写满。
- 并发优先减少墙钟等待，不宣称固定token/费用节省；缺少可信计量时不建额外探针。
